Help

  • Nothing is sent anywhere: decoding, signing and verifying run in this page with the browser's Web Crypto.
  • The token and keys are kept only for this tab, up to 2 MB. Reloading restores them; a new tab starts fresh. Light / dark applies to every tool.

Editing

  • Every panel is editable. Edit the encoded token and the header and payload follow. Edit the header or payload and the token is rebuilt and signed again with the key below.
  • Without a key that can sign (a long enough secret, or a private key), the token keeps its old signature, which then no longer verifies.
  • The algorithm is the header's alg. Choosing another one rewrites the header and signs again; if there is no key for it yet, one is generated.
  • Orange, violet and green mark the header, payload and signature, in the token and in the panel titles.
  • Known header parameters and claims are explained at the end of their line, with exp, nbf and iat as local dates and how long ago or ahead they are. The notes are not part of the JSON: they are not copied or signed. JSON written on one line gets no notes.
  • With the token cleared, typing a payload starts a new token with a default header.
  • A token pasted with its Bearer prefix, or wrapped over several lines, is made compact as it is pasted.

Keys

  • HS256, HS384 and HS512 use a shared secret, as UTF-8 text, Base64url, Base64, hex or an oct JWK. Changing the encoding rewrites the secret in it, so the key stays the same; if the text was already written in the new encoding, a button reads it that way instead. Signing needs at least 32, 48 or 64 bytes; verifying accepts any length.
  • RS, PS, ES and EdDSA verify with the public key and sign with the private key, each as PEM (SPKI public / PKCS#8 private) or JWK. With only a private key, its public half is used to verify.
  • Under each key, a line says whether it is a valid secret, public key or private key for the algorithm. Generate key makes a fresh random secret (as text) or key pair for the algorithm and signs the token with it. Sign token signs the current header and payload with the key as it is.

What the checks mean

  • Valid JWT: three Base64url parts, with a strict JSON header and payload and an alg. Signature verified: the key matches the signature.
  • alg none is an unsigned token: its signature is empty, and there is nothing to verify. Encrypted tokens (JWE, five parts) show only their header.
  • Neither says the claims should be trusted: issuer, audience and authorization are for the service that receives the token. Expiry and not-before are shown for reference.
  • exp, nbf and iat are Unix seconds. Duplicate member names, crit and unencoded payloads (b64) are refused.
